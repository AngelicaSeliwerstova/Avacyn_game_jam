# gamek

Реализуем PSX-игру от первого лица с нуля, постепенно.

- Пишем собственный код; готовую реализацию Wolfenstein-3D-Clone не используем.
- Двигаемся по одному небольшому шагу с объяснением и проверкой результата.
- Первый шаг выполнен: минимальное окно и игровой цикл на Python и Pygame.
- Второй шаг выполнен: код разделён на настройки, системы движка и пакет игры.
- Третий шаг выполнен: OpenGL 3.3, ModernGL и первый цветной треугольник.
- Четвёртый шаг выполнен: перспективная камера, буфер глубины и 3D-куб.
- Пятый шаг выполнен: WASD, обзор мышью, захват курсора и управление фокусом.
- Шестой шаг выполнен: клетчатый пол, описание уровня и столкновения со скольжением.
- Седьмой шаг выполнен: коридор с правым поворотом, загрузка TMX и старт из карты.

Исходное [техническое задание](docs/SPEC.md) сохранено как описание желаемой игры. Указания в нём использовать готовый проект и запускать исходник заменены решением писать игру с нуля.

## Шаг 1. Окно и игровой цикл

Нужен Python 3.13 x64; проверенная версия — 3.13.7. Открой PowerShell в папке проекта и один раз установи окружение:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Запуск:

```powershell
.\.venv\Scripts\python.exe main.py
```

Появится окно размером 1280×960 с коридором на клетчатом полу. Пройди вперёд и поверни направо в конце первой части. WASD — ходьба, мышь — обзор. Esc освобождает мышь и останавливает управление камерой, клик по окну возвращает управление. Закрытие — крестиком или Alt+F4. Нужен драйвер с поддержкой OpenGL 3.3. Внутреннее разрешение 320×240 добавим отдельным шагом.

На первом шаге игровой цикл находился в `main.py`. Теперь он перенесён в `engine/core/application.py`. На первом шаге он работал так:

1. `pygame.init()` включает модули Pygame, `set_mode()` создаёт окно.
2. Цикл `while running` повторяет работу программы каждый кадр.
3. `pygame.event.get()` получает события; крестик и Esc завершают цикл.
4. `screen.fill()` заливает фон, `pygame.display.flip()` показывает кадр.
5. `clock.tick(60)` ограничивает частоту кадров до 60, `pygame.quit()` освобождает ресурсы при выходе.

Проверено 26 октября 2026 года: создание настоящего окна 1280×960, заливка фона, выход по событию закрытия окна и по Esc, освобождение ресурсов. `pip check` ошибок зависимостей не обнаружил.

## Шаг 3. ModernGL и первый треугольник

Если окружение уже установлено, обнови зависимости и запусти приложение:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

Версии пакетов: Pygame 2.6.1, ModernGL 5.13.0, glcontext 3.1.0.

Как строится кадр:

1. `Window` создаёт окно с OpenGL 3.3 Core и двойной буферизацией. MSAA отключено.
2. `Renderer` подключается к контексту окна, читает и компилирует шейдеры.
3. `TriangleMesh` передаёт на видеокарту три вершины. Каждая содержит позицию XYZ и цвет RGB. Буфер создаётся один раз при запуске.
4. `triangle.vert` задаёт положение каждой вершины на экране. На третьем шаге координаты указаны напрямую в пространстве отсечения, без камеры.
5. `triangle.frag` задаёт цвет фрагмента. Между вершинами цвета плавно интерполируются.
6. Каждый кадр `Renderer` очищает фон и рисует треугольник, затем `Window.present()` показывает результат.
7. При выходе освобождаются геометрия, шейдерная программа и контекст ModernGL; после этого закрывается окно Pygame.

Шейдеры загружаются относительно `renderer.py`, поэтому запуск из другой рабочей папки также работает. Параметры проекта по-прежнему передаются движку через `main.py`.

Проверено 26 октября 2026 года на Intel UHD Graphics, OpenGL 3.3.0, драйвер 31.0.101.4146: по 30 кадров в окнах 1280×960 и 640×480, цвет фона и три области цвета треугольника, отсутствие ошибок OpenGL, выход по крестику и Esc, освобождение GPU-ресурсов. Дополнительно проверено завершение при ошибке чтения шейдера. `pip check` ошибок зависимостей не обнаружил. Проверочный кадр сохранён локально в `artifacts/step03-triangle.png`; артефакты не включаются в Git.

## Шаг 4. Перспективная камера и 3D-куб

Установлена новая зависимость PyGLM 2.8.3 для векторов и матриц. Для повторной установки на другом компьютере:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

Камера находится в `engine/scene/camera.py`. `main.py` создаёт её из настроек и передаёт в приложение, а приложение — в рендерер. Движок по-прежнему не импортирует настройки игры.

Параметры камеры в `config/settings.py`:

```python
CAMERA_POSITION = (3.0, 2.0, 4.0)
CAMERA_TARGET = (0.0, 0.0, 0.0)
CAMERA_FOV_DEGREES = 60.0
CAMERA_NEAR = 0.1
CAMERA_FAR = 100.0
```

`POSITION` — откуда смотрим, `TARGET` — в какую точку. Ось Y направлена вверх. `FOV_DEGREES` задаёт вертикальный угол обзора; `NEAR` и `FAR` ограничивают видимый диапазон глубины. Параметры применяются после перезапуска.

В `color.vert` положение вершины теперь вычисляется так:

```glsl
gl_Position = m_projection * m_view * m_model * vec4(in_position, 1.0);
```

- `m_model` размещает объект в мире. Сейчас это единичная матрица: куб находится в начале координат, без поворота и масштабирования.
- `m_view` переводит мировые координаты в систему камеры.
- `m_projection` задаёт перспективу и учитывает соотношение сторон окна.

`CubeMesh` в `engine/rendering/meshes/cube.py` создаёт куб со стороной 2: шесть граней, 12 треугольников, 36 вершин. Каждая сторона имеет свой цвет. Буфер глубины и `DEPTH_TEST` позволяют ближним поверхностям перекрывать дальние независимо от порядка рисования. При каждом кадре очищаются и цвет, и глубина.

Демонстрация треугольника заменена кубом, а шейдеры переименованы в `color.vert` и `color.frag`. Предыдущая версия доступна в истории Git. Камера на этом шаге фиксирована.

Проверка: по 15 кадров в окнах 1280×960 и 960×540 с разными FOV и противоположными позициями камеры; подтверждены цвета трёх видимых граней в каждом ракурсе и скрытие остальных. Проверены границы ближней и дальней плоскостей, выход по крестику и Esc, освобождение GPU-ресурсов, отсутствие ошибок OpenGL. `pip check` прошёл. Проверочный кадр — `artifacts/step04-cube.png`.

## Шаг 5. Управление от первого лица

Запуск прежний; дополнительных зависимостей нет:

```powershell
.\.venv\Scripts\python.exe main.py
```

Управление:

- WASD — движение относительно горизонтального направления взгляда.
- Мышь — поворот камеры. Наклон вверх и вниз ограничен ±80°.
- Esc — освободить мышь и остановить управление камерой.
- Левая кнопка мыши внутри активного окна — вернуть управление.
- При потере фокуса мышь освобождается; после возвращения в окно нужно кликнуть.
- Крестик окна или Alt+F4 — выйти.

При запуске мышь захватывается, если окно получило фокус. Высота камеры сохраняется; направление взгляда не превращает ходьбу в полёт. Освобождение мыши сейчас отключает ввод камеры; полноценные состояния игры и меню появятся позже.

Разделение ответственности:

- `config/controls.py` задаёт клавиши и кнопку мыши через `InputBindings`.
- `KeyboardMouse` в `engine/input` читает состояние клавиш и относительное смещение мыши. При освобождённой мыши или отсутствии фокуса возвращает нулевой ввод. Первый отсчёт мыши после захвата отбрасывается, чтобы избежать скачка обзора.
- `FirstPersonController` в `engine/controllers` получает оси движения, смещение мыши и время кадра. Он не зависит от Pygame и меняет только положение и направление камеры.
- `Application` читает время в секундах, передаёт ввод контроллеру и вызывает рендерер. При выходе освобождает мышь, GPU-ресурсы и окно.

Настройки движения в `config/settings.py`:

```python
MOVE_SPEED = 2.5
MOUSE_SENSITIVITY = 0.12
PITCH_LIMIT_DEGREES = 80.0
MAX_DELTA_TIME = 0.1
```

Скорость задана в мировых единицах в секунду, чувствительность — в градусах на пиксель. Вектор движения нормализуется, поэтому диагональ не ускоряет камеру. Смещение мыши не умножается на время кадра. Шаг движения ограничен 0,1 секунды: длительная задержка не вызывает большого скачка положения; при FPS ниже 10 движение будет замедляться относительно реального времени.

Проверки:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Все 12 тестов прошли: расстояние 25 единиц за 10 секунд при 30/60/120 FPS, диагональная скорость, сохранение высоты, предел наклона, направление ходьбы после поворота, одинаковый поворот при одинаковом пути мыши, ограничение шага после задержки, встречные клавиши, переназначение управления, Esc, фокус и отсутствие скачка мыши после захвата.

Также проверены 20 кадров в настоящем OpenGL-окне с программно заданным вводом: движение, остановка по Esc, продолжение кликом, потеря/возврат фокуса, отрисовка куба и освобождение ресурсов. На этой автоматической проверке вызовы захвата мыши заменены заглушками, чтобы не забирать курсор рабочего стола. Кадр — `artifacts/step05-first-person.png`.

## Шаг 6. Пол и столкновения

Команда запуска и управление прежние. Дополнительных зависимостей нет.

В сцене есть клетчатый пол размером 20×20 м на `Y = 0` и куб размером 2×2×2 м с центром на `Y = 1`. Игрок имеет горизонтальный радиус 0,25 м, камера находится на высоте 1,6 м. Движение остаётся на одном этаже. Граница пола ограничивает движение так, чтобы весь круг игрока оставался на площадке.

Настройки в `config/settings.py`:

```python
PLAYER_EYE_HEIGHT = 1.6
CAMERA_POSITION = (3.0, PLAYER_EYE_HEIGHT, 4.0)
CAMERA_TARGET = (0.0, 1.0, 0.0)
PLAYER_RADIUS = 0.25
COLLISION_MAX_STEP = 0.1

FLOOR_SIZE = (20.0, 20.0)
FLOOR_TILE_SIZE = 1.0
CUBE_SIZE = (2.0, 2.0, 2.0)
CUBE_POSITION = (0.0, CUBE_SIZE[1] / 2, 0.0)
```

Как связаны данные:

1. `game/levels/demo.py` собирает `Level` из настроек.
2. `Box` задаёт положение и размер препятствия. Его `model_matrix` используется для отрисовки, а `footprint` — для прямоугольного коллайдера. Они вычисляются из одних данных.
3. `main.py` строит `CollisionWorld`, передаёт его контроллеру, а описание уровня — приложению и рендереру.
4. `FloorMesh` один раз загружает клетчатый пол в GPU-буфер. `Renderer` рисует пол и объекты уровня; геометрия куба переиспользуется.

Как работает столкновение:

- `AABB` описывает прямоугольник, стороны которого параллельны осям X и Z.
- Игрок представлен кругом. На углах используется расстояние до ближайшей точки прямоугольника, поэтому радиус не превращается в квадрат.
- Перемещение разбивается на подшаги. Движение по X и Z разрешается отдельно: заблокированная составляющая останавливается, свободная продолжает движение вдоль грани.
- На каждой оси проверяется весь отрезок перемещения до границы препятствия. Это предотвращает перескок через тонкую стену даже при большой длине запрошенного движения.
- Положение по Y сохраняется. Это система столкновений для одноэтажного уровня; прыжки и гравитация здесь не рассчитываются.
- Старт внутри препятствия или за границей пола отклоняется до открытия окна.

Проверки запускаются той же командой:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Все 25 тестов прошли. Новые проверки охватывают четыре грани куба, скольжение по диагонали, круг на углу, непроходимый стык двух стен, стену толщиной 0,001 м, разные радиусы, границу пола, 500 последовательных перемещений, остановку при 30/60/120 FPS и совпадение размеров модели с коллайдером.

Дополнительно проверены настоящие OpenGL-окна: 15 кадров исходной сцены и 35 кадров с программно заданной ходьбой в куб. Подтверждены отрисовка пола и граней, высота камеры, остановка центра игрока на расстоянии 0,25 м от грани, отсутствие ошибок OpenGL и освобождение ресурсов. Ввод и захват мыши на этой автоматической проверке заданы программно. Кадр — `artifacts/step06-floor-collision.png`.

## Шаг 7. Коридор с поворотом и карта Tiled

Добавлена зависимость PyTMX 3.32. При установке проекта заново используй актуальный `requirements.txt`:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

По умолчанию запускается коридор. Переключение сцен находится в `config/settings.py`:

```python
LEVEL_NAME = "corridor"  # Коридор с поворотом.
# LEVEL_NAME = "demo"   # Предыдущая площадка с кубом.
```

У каждой сцены теперь свой старт в `Level`. Для кубовой сцены он берётся из `CAMERA_POSITION` и `CAMERA_TARGET`, для коридора — из карты. Высота игрока, FOV и управление по-прежнему находятся в общих настройках.

Карта `resources/levels/corridor.tmx` имеет размер 10×10 клеток. Одна клетка соответствует 2 м, ширина прохода — 4 м, высота стен — 2,8 м. План сверху (`#` — стена, `.` — проход):

```text
##########
#........#
#........#
#..#######
#..#######
#..#######
#..#######
#..#######
#..#######
##########
```

Старт находится в нижней части вертикального прохода. Нужно идти к верхнему проходу и повернуть направо. Обе крайние точки закрыты стенами; это тестовая сцена для движения и графики.

Редактирование в Tiled:

- Открой `resources/levels/corridor.tmx`. Для запуска игры сам редактор не требуется.
- На слое `walls` рисуй стены единственным тайлом. Пустые клетки образуют проходы.
- На объектном слое `spawn` перемещай точку `player`. Свойство `yaw_degrees` задаёт направление: −90° — вверх по карте, 0° — вправо, 90° — вниз, 180° — влево.
- Свойства карты `cell_size`, `wall_height` и `floor_tile_size` задают размеры в мировых единицах. Размер редакторской клетки 32×32 пикселя используется для перевода координат карты в мир.
- Сохраняй имена слоёв `walls`, `spawn` и объекта `player`. Карта должна быть конечной и ортогональной. Изменения применяются после перезапуска игры.

Загрузчик `engine/scene/tiled_level.py` создаёт из заполненных клеток объекты `Box`. Рендерер и коллизии используют одни и те же размеры. Координата X карты становится X мира, Y карты — Z мира; центр карты совпадает с началом мировых координат. Положение и направление старта загружаются в `Level`, затем `main.py` создаёт камеру из этих данных.

Пол пока общий, стены рисуются цветными гранями, верх коридора открыт. Значок `wall.png` создан в проекте для редактора. Следующие визуальные шаги будут добавляться поверх этой геометрии.
